### Bug Fixes

- **Alarms die after days unopened (BUG-01)** — Each alarm had a single AlarmKit registration. AlarmKit never launches the app on fire, so once iOS terminated the process nothing registered the next occurrence. `AlarmScheduler` now pre-registers up to 12 future occurrences per time slot (400-day cap) using derived IDs that resolve back to `Alarm.id` through a persisted map.
- **In-app snooze fired at the wrong time** — `scheduleAlarm` recomputed from the schedule and ignored `nextFireDate`. Snoozed alarms now register their primary ID at the snooze expiry.
- **Multi-time alarms cancelled as stale** — Secondary time slots use derived AlarmKit IDs that the `.alerting` handler could not match to a model, so it cancelled them. All AlarmKit lookups now go through `AlarmScheduler.activeRegistration` / `baseAlarmID` / `stopActiveRegistration`.

### What to Watch

- AlarmKit registration count per alarm is now up to 12 × time slots. Watch for any AlarmKit scheduling errors in Crashlytics under `alarm_schedule`.
- Backup `UNNotification` and pre-alarm notifications still cover only the first occurrence.
- Device verification still pending: create a weekly alarm, force-quit, let it fire, confirm the next registration survives.
